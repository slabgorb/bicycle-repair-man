# Bicycle Repair Man (BRM) v0.2 — Orchestrator-aware

**Date:** 2026-05-12
**Status:** Design approved; pending implementation plan.
**Predecessors:** v0.1.0 design at `docs/superpowers/specs/2026-05-12-brm-design.md` (single-repo plugin); Pennyfarthing's `pf git` and `.pennyfarthing/repos.yaml` (referenced for prior art only — no code or schema is reused verbatim).

## Problem statement

v0.1.0 of BRM is single-repo. The hook finds a `.git` (or `.brm/sidecars/`) ancestor, calls it the project root, and reads at most two sidecar layers (global + project). For workspaces where one parent directory holds multiple sibling repos (the "orchestrator pattern" — e.g. `orc-penny/` containing `pennyfarthing/` and others), a single project root is wrong: roles need to know which repo the cwd is in *and* what other repos exist around it.

v0.2 introduces:

1. A BRM-owned `.brm/repos.yaml` at the **orchestrator root** declaring the repos that make up the workspace.
2. A **third sidecar layer** (`<orchestrator_root>/.brm/sidecars/<role>.md`) between global and per-repo.
3. An eager **`<brm-orchestrator>`** context block injected by the hook when an orchestrator workspace is detected.
4. A **`scripts/brm-repos`** Python CLI that exposes introspection (list/topology/describe/owns) and multi-repo git operations (status/snapshot/branch), invoked by roles via Bash at `${CLAUDE_PLUGIN_ROOT}/scripts/brm-repos`.
5. An **orchestrator-awareness addendum** in each of the six v0.1.0 role briefs explaining what to do when `<brm-orchestrator>` is present.

Out of scope for v0.2 (deferred to v0.3): workflow definitions and gates that span multiple repos; cross-repo handoff choreography; the worktree fan-out (`brm-repos worktree`); test/lint/build runner scripts (roles can `cd <repo> && <command>` directly using the injected topology).

## Decisions

| Decision | Choice |
|---|---|
| Marker | `<orchestrator_root>/.brm/repos.yaml` (BRM-owned; no coupling to PF) |
| Schema | Closed, practical subset: `path / type / description / default_branch / test_command / lint_command / build_command` |
| Awareness model | Eager injection — hook emits `<brm-orchestrator>` block alongside `<brm-sidecar>` |
| Sidecar layering | 3 layers (global → orchestrator → repo); 2 layers when only orchestrator OR only repo present; falls back to v0.1.0 behavior when neither orchestrator nor repo is detected |
| Roster | Unchanged at 6 roles (TEA / Dev / Reviewer / Architect / PM / Tech Writer) |
| Invocation | Bash only — roles call `${CLAUDE_PLUGIN_ROOT}/scripts/brm-repos`; no slash commands |
| Implementation | Python stdlib + `pyyaml>=6.0`; mirrors v0.1.0's zeitgoose-flavored layout |
| Discovery cap | 20-level walk, consistent with v0.1.0's `find_project_root` |

## Section 1 — Architecture & composition

### Hook wire diagram (one turn, `/reviewer look at the cache change` from inside `orc-penny/pennyfarthing/`)

```
Claude Code receives prompt
   │
   ├─ UserPromptSubmit hook fires:
   │   ├─ Detect leading token `/reviewer` → role = reviewer
   │   ├─ Walk up from cwd:
   │   │   ├─ find_orchestrator_root: orc-penny/.brm/repos.yaml found
   │   │   └─ find_project_root: orc-penny/pennyfarthing/.git found
   │   ├─ Resolve cwd-repo from repos.yaml: pennyfarthing
   │   ├─ load_sidecar with 3 layers (global, orchestrator, repo)
   │   ├─ Parse repos.yaml into <brm-orchestrator> block
   │   └─ Emit additionalContext = "<brm-sidecar>...</brm-sidecar>\n<brm-orchestrator>...</brm-orchestrator>"
   │
   ├─ Slash command resolves: commands/reviewer.md is the role brief
   │
   └─ Claude sees:
       user message + brm-sidecar + brm-orchestrator + role brief
       → operates as Reviewer with full multi-repo context
```

### Properties

- **Strictly additive.** A repo that has no orchestrator parent behaves exactly as in v0.1.0. The hook does not break for v0.1.0-style workspaces.
- **Independent walks.** Orchestrator root and project (repo) root are resolved by separate walks. They may be different directories (typical orchestrator case), the same directory (orchestrator root has its own `.git`), or only one of the two may exist.
- **One-shot injection.** Same as v0.1.0 — the orchestrator block injects only on the role-activation turn. Bare turns inject nothing. No "currently in orchestrator mode" state is kept anywhere.
- **No daemon, no shared state.** Each plugin's hook fires independently (BRM + Zeitgoose unchanged).
- **Stateless script.** `scripts/brm-repos` re-resolves the orchestrator root on every invocation. No caching.

## Section 2 — Schema & marker

### Filesystem

```
<orchestrator_root>/.brm/
├── repos.yaml                     # marker + config (REQUIRED for orchestrator mode)
└── sidecars/                      # orchestrator-level sidecars (OPTIONAL)
    ├── tea.md
    ├── dev.md
    ├── reviewer.md
    ├── architect.md
    ├── pm.md
    └── tech-writer.md

<orchestrator_root>/<repo.path>/
├── .git/                          # each declared repo is a real git repo
└── .brm/sidecars/                 # repo-level sidecars (OPTIONAL)
    └── <role>.md
```

### `repos.yaml` schema

```yaml
repos:
  <short-name>:                    # alphanumeric + hyphen + underscore, [a-z0-9_-]+
    path: <relative path>          # REQUIRED; relative to the directory containing .brm/repos.yaml
    type: <free string>            # REQUIRED; convention: api, ui, framework, orchestrator, lib, …
    default_branch: <branch>       # REQUIRED; e.g. main, develop
    test_command: <shell string>   # REQUIRED; empty string allowed if the repo has no test runner
    lint_command: <shell string>   # REQUIRED; empty string allowed
    description: <one-liner>       # OPTIONAL; defaults to "" if omitted
    build_command: <shell string>  # OPTIONAL; defaults to "" if omitted
```

Rules:

- The top-level document MUST be a mapping with a `repos` key. Additional top-level keys are reserved for v0.3+ and produce a warning to stderr (from both the hook and `brm-repos`); they are ignored, not rejected.
- Each repo entry is keyed by a short name; this name appears in the `<brm-orchestrator>` block and is the argument to `brm-repos describe` / `brm-repos owns` output.
- `path` is interpreted relative to the directory **containing** `.brm/`, not relative to `.brm/`. A repo `path: .` is valid and means the orchestrator root is itself a repo.
- Unknown per-repo fields produce a warning to stderr and are ignored.
- A YAML parse error → orchestrator block is dropped; sidecars still emit; hook exits 0.

### Example (orc-penny-shaped)

```yaml
repos:
  orchestrator:
    path: .
    type: orchestrator
    description: Sprint management and framework development coordination
    default_branch: main
    test_command: ""
    lint_command: ""
    build_command: ""
  pennyfarthing:
    path: pennyfarthing
    type: framework
    description: Pennyfarthing framework source (inlined for development)
    default_branch: develop
    test_command: pnpm test
    lint_command: pnpm lint
    build_command: pnpm build
```

## Section 3 — Sidecar layering

Three layers, injected in **most-general to most-specific** order so the most-specific lessons appear last (and are most salient to the model):

1. **Global** — `~/.claude/brm/sidecars/<role>.md`
2. **Orchestrator** — `<orchestrator_root>/.brm/sidecars/<role>.md`
3. **Repo** — `<repo_root>/.brm/sidecars/<role>.md`

Layer presence rules:

| Workspace shape | Layers emitted |
|---|---|
| No orchestrator, no project root | Global only (if it exists) |
| Project root only (v0.1.0 single-repo case) | Global + Repo |
| Orchestrator root only (cwd at orchestrator root, no subrepo containing cwd) | Global + Orchestrator |
| Both orchestrator and project root | Global + Orchestrator + Repo |

The emitted XML uses the same shape as v0.1.0 with an added `scope="orchestrator"` value:

```
<brm-sidecar role="reviewer">
  <layer scope="global" path="~/.claude/brm/sidecars/reviewer.md">
…verbatim contents…
  </layer>
  <layer scope="orchestrator" path=".brm/sidecars/reviewer.md">
…verbatim contents…
  </layer>
  <layer scope="project" path=".brm/sidecars/reviewer.md">
…verbatim contents…
  </layer>
</brm-sidecar>
```

`<layer>` block omission rules unchanged from v0.1.0: a missing-or-unreadable file silently drops just that layer. If all three layers are missing/unreadable, the whole `<brm-sidecar>` block is suppressed.

## Section 4 — `<brm-orchestrator>` injection

### Format

```
<brm-orchestrator root="<absolute path>" cwd-repo="<short-name-or-omitted>">
<repos.yaml>
<verbatim contents of repos.yaml>
</repos.yaml>
</brm-orchestrator>
```

Attributes:

- `root` — absolute path to the orchestrator root (the directory containing `.brm/repos.yaml`).
- `cwd-repo` — short name of the repo whose `path` contains cwd, by closest-ancestor match. Omitted entirely if cwd does not sit under any declared repo's `path`.

The body wraps the file's verbatim text in a `<repos.yaml>` element. No translation. No comment stripping. No re-serialization. This preserves the file as the source of truth and avoids drift bugs in the renderer.

### Emission rules

- The hook emits `<brm-orchestrator>` **only** when:
  1. The leading token is a recognized role command (same trigger as v0.1.0), **and**
  2. `find_orchestrator_root(cwd)` returns a non-None directory, **and**
  3. `.brm/repos.yaml` parses as valid YAML, **and**
  4. The parsed document has a `repos:` top-level key whose value is a non-empty mapping.
- If any of those conditions fails, the orchestrator block is omitted. The sidecar block (if any) still emits — orchestrator awareness is additive.
- Both blocks are emitted in the same `additionalContext` string, sidecar first, then orchestrator, separated by a single newline.

## Section 5 — Discovery walk

Two independent walks, each capped at 20 ancestor steps. Both start from cwd (or the event's `cwd` field, or `BRM_PROJECT_ROOT` / `BRM_ORCHESTRATOR_ROOT` env-var overrides for tests).

### `find_orchestrator_root(cwd) -> Path | None`

Walks up from cwd. For each ancestor, returns it if `<ancestor>/.brm/repos.yaml` is a regular file. Returns `None` if the cap is reached without a match.

### `find_project_root(cwd) -> Path | None`

Refines v0.1.0's logic. The marker is now **`.git` (file or dir) OR `.brm/sidecars/` (directory)**. An orchestrator's `.brm/` without a `sidecars/` subdirectory must not register as a project root — otherwise the orchestrator root would be misinterpreted as a project. The v0.1.0 test for `find_project_root_finds_brm_dir` is updated to check `.brm/sidecars/` instead of bare `.brm/`. This is a small behavior change documented in the migration note (Section 9).

### `cwd_repo(cwd, orchestrator_root, repos) -> str | None`

Given the parsed `repos` map and the orchestrator root, returns the short-name of the repo whose `<orchestrator_root>/<repo.path>/` is the closest ancestor of cwd. Returns `None` if no declared repo contains cwd.

Implementation: resolve each repo's absolute path, sort by descending path length, return the first that is an ancestor (or equal). A repo with `path: .` matches the orchestrator root itself.

### Combination rules

The hook performs both walks independently. Within an orchestrator, the project root will typically be `<orchestrator_root>/<repo.path>` for the cwd-repo, but the two walks are NOT required to align — the hook handles each layer's resolution separately:

- Orchestrator sidecar layer: read from `<orchestrator_root>/.brm/sidecars/<role>.md`.
- Repo sidecar layer: read from `<find_project_root(cwd)>/.brm/sidecars/<role>.md`.
- These may resolve to different directories (e.g., cwd is somewhere unusual). The hook does not try to reconcile them; it just reads what's there.

## Section 6 — Script surface (`scripts/brm-repos`)

A single Python script with eight subcommands. Stdlib `argparse` for parsing. `pyyaml` for parsing `repos.yaml`. No other runtime dependencies.

Located at `<plugin_root>/scripts/brm-repos`. Executable, shebang `#!/usr/bin/env python3`. Implementation logic lives in `lib/orchestrator.py` (re-used by the hook).

| Subcommand | Surface | Behavior | Exit code |
|---|---|---|---|
| `init [--from-pf] [--force]` | `--from-pf` reads `.pennyfarthing/repos.yaml` from cwd and translates to BRM schema (see translation rules below). `--force` overwrites an existing file. | Always writes to `<cwd>/.brm/repos.yaml`; creates the `.brm/` directory if absent. Refuses if the target file exists and `--force` is not set. | 0 / 1 |
| `list [--json]` | — | Print one short-name per line; `--json` returns array of `{name, path, type}`. | 0 |
| `topology [--json]` | — | `--json` parses and re-emits as JSON; otherwise prints the verbatim file. | 0 |
| `describe <name> [--json]` | `<name>` is a short-name. | Print the per-repo block. Errors if name unknown. | 0 / 2 |
| `owns <path>` | `<path>` is any path (relative to cwd or absolute). | Print the short-name of the closest containing repo. Errors if no repo matches. | 0 / 2 |
| `status [--brief] [--json]` | — | `git status --porcelain` aggregated per repo. `--brief` prints one line per repo. Exits 1 if any repo is dirty or has unpushed commits. | 0 / 1 |
| `snapshot [--label LABEL]` | — | In each dirty repo: create `snapshot/YYYY-MM-DDTHH-MM-SS-<label>` branch from current HEAD, `git add -A`, `git commit -m "snapshot: <label>"`, return to original branch. Skips clean repos. | 0 / 1 |
| `branch <name> [--repos all\|csv]` | `<name>` is the new branch name. `--repos` filters target repos (default `all`). | For each selected repo: `git fetch origin <default_branch>` (best-effort), then `git switch -c <name> origin/<default_branch>`. Skips repos where the branch already exists. | 0 / 1 |

### `init --from-pf` translation rules

When `--from-pf` is set and `<cwd>/.pennyfarthing/repos.yaml` exists, the script:

- Copies `repos.<name>.path`, `type`, `description`, `default_branch` verbatim.
- Copies `repos.<name>.test_command`, `lint_command`, `build_command` if present; defaults each to `""` if absent.
- Drops PF-specific fields (`owns`, `never_edit`, `symlinks`, `ui_layer`, `components_path`, `branch_strategy`, `language`, `notes`, `pr_title_format`, `gates`) — these are recorded only as a stderr summary line: `"dropped <N> PF-only fields; see docs/orchestrator-schema.md"`.
- If `.pennyfarthing/repos.yaml` is missing or unparseable, exits 1 with a clear error; does not write a partial file.

### Errors

- Exit 2 — usage error (unknown subcommand, missing required arg, unknown repo name passed to `describe`).
- Exit 1 — runtime failure (git command failed; `repos.yaml` unparseable; file exists for `init` without `--force`; any repo is dirty/unpushed for `status`; `--from-pf` source missing; etc.).
- Exit 0 — success.

### Env-var test overrides

- `BRM_ORCHESTRATOR_ROOT` — bypasses the `find_orchestrator_root` walk. The script trusts this path is an orchestrator root and uses it directly.
- (`BRM_HOME` and `BRM_PROJECT_ROOT` from v0.1.0 remain.)

### Output stability

All `--json` outputs are documented as stable surfaces from v0.2.0 onward. Text outputs are NOT stable — they're for human reading; tooling should use `--json`.

## Section 7 — Role brief addendum

Each of the six v0.1.0 role briefs gets a new H2 section, inserted after **`## Skills you invoke`** and before **`## Sidecar protocol`**:

```markdown
## Orchestrator awareness

If a `<brm-orchestrator>` block is present in your context, you're in a
multi-repo workspace. Operating notes:

- The block lists every repo, its `path`, `type`, `default_branch`, and
  the per-repo `test_command` / `lint_command` / `build_command`.
- `cwd-repo` (if set) names the repo containing the current working
  directory. If unset, you're at the orchestrator root or in an
  undeclared subdirectory.
- For "which repo owns this file?" run:
  `${CLAUDE_PLUGIN_ROOT}/scripts/brm-repos owns <path>`
- For status across all repos:
  `${CLAUDE_PLUGIN_ROOT}/scripts/brm-repos status`
- When a plan or handoff spans repos, name each repo explicitly
  (e.g., "ready for `/dev` in `api`").

If no `<brm-orchestrator>` block appears, you're in single-repo mode —
ignore this section.
```

The addendum is the same wording in every brief, with one exception: in `commands/architect.md` and `commands/pm.md`, append one extra bullet to the **What you do** section: *"When the workspace is an orchestrator, name affected repos in plans/scopes explicitly."* This keeps planning-shaped roles on the hook for cross-repo coordination without adding a new role.

The lint test (`tests/test_commands_parse.py`) gains the new required section to its `REQUIRED_H2_SECTIONS` list. Word-budget cap bumps from 750 to 900 to absorb the addendum.

### Error handling

| Failure | Behavior |
|---|---|
| `repos.yaml` malformed (YAML parse error) | Hook drops orchestrator block; sidecars still emit; stderr log; exit 0. Scripts exit 1 with a parse-error message. |
| `repos.yaml` exists, parses, missing required field | Same as malformed for the hook. Scripts exit 1 with a schema-error message naming the missing field. |
| Repo listed in `repos.yaml` but its `path` doesn't exist on disk | `brm-repos list` still lists it; `topology` shows it with a `<warning>missing on disk</warning>` annotation in the JSON output; `status`/`snapshot`/`branch` skip it with a warning. |
| pyyaml not installed | Hook exits 0 with stderr error (`ModuleNotFoundError`); sidecar block still emits (load_sidecar doesn't need yaml). Scripts exit 1 with a clear install hint. Plugin metadata installs pyyaml as part of `dev` extras; users running the script need it on path. |
| Walk-cap reached without finding `.brm/repos.yaml` | Treat as non-orchestrator workspace. |
| `BRM_ORCHESTRATOR_ROOT` env var points to a directory with no `.brm/repos.yaml` | Treat as if no orchestrator root were found. (No "you told me this was an orchestrator but it isn't" error — env var is for test convenience, not user-facing config.) |

### Testing

Additions on top of the v0.1.0 test suite. Pytest, stdlib + pyyaml only. CI on Python 3.11 + 3.12.

1. **`test_orchestrator.py`** — unit tests for `find_orchestrator_root` (found, not found, cap reached, walk stops at first match in nested case), `cwd_repo` (each repo matched, no repo matches, `path: .` orchestrator-as-repo case), `parse_repos_yaml` (happy path, malformed, missing required field, unknown key emits warning).

2. **`test_brm_repos_cli.py`** — subprocess golden-output tests for each of the eight subcommands. Cases: `init` from scratch, `init --from-pf`, `init --force`, `list`/`topology`/`describe`/`owns` happy paths plus error paths, `status` with clean and dirty fixtures (using `tmp_path` to create real git repos), `snapshot` and `branch` with dry verification via `git log` / `git branch --list`. JSON outputs validated against documented shape.

3. **`test_hook_output.py`** — new cases for orchestrator scenarios: orchestrator + 3 layers, orchestrator + no repo sidecar, orchestrator-root-only (no repo containing cwd), malformed `repos.yaml` falls back gracefully. Existing v0.1.0 tests must still pass.

4. **`test_sidecar_paths.py`** — adds tests for `load_sidecar` with `orchestrator_root` arg. The existing test for `find_project_root_finds_brm_dir` is updated to use `.brm/sidecars/` as the marker (see Section 9).

5. **`test_commands_parse.py`** — the `REQUIRED_H2_SECTIONS` list adds `## Orchestrator awareness` between `## Skills you invoke` and `## Sidecar protocol`. Word budget cap bumps to 900.

6. **`test_hook_perf.py`** — unchanged. The orchestrator-mode match path will be slower than v0.1.0 (extra walk + YAML parse), but should still beat the 250ms median budget. If it doesn't, the budget is wrong for v0.2 — we re-tune rather than accept regressions.

## Section 9 — Migration from v0.1.0

For existing v0.1.0 users (single-repo workspaces): **nothing changes**. The hook behavior is strictly additive — when no `.brm/repos.yaml` is found, the orchestrator block is omitted, and sidecar resolution falls back to the 2-layer model.

**One behavior tweak:** the v0.1.0 marker for `find_project_root` was `.git OR .brm/`. v0.2 narrows it to `.git OR .brm/sidecars/`. The reason: an orchestrator root has a `.brm/repos.yaml` and (often) no `.brm/sidecars/`. Without this narrowing, every orchestrator root would also be misidentified as a project root.

In practice, no v0.1.0 user is harmed:

- The role briefs Already tell roles "create `.brm/sidecars/<role>.md` if it doesn't exist." Anyone with a working v0.1.0 project sidecar already has the `sidecars/` subdir.
- The only break is for someone who created a bare `.brm/` dir but no sidecar files. Their project root resolution would now fail. This is so unusual it's not worth a compatibility shim.

The CHANGELOG / release notes call this out explicitly.

## Section 10 — Out of scope for v0.2 (deferred backlog)

- **Cross-repo workflow choreography.** Workflow YAML that names multiple repos, gates that wait on signals from multiple repos, handoff markers that carry repo context. → v0.3.
- **Cross-repo TDD discipline.** A failing test in one repo blocking implementation in another. → v0.3.
- **Worktree fan-out** (`brm-repos worktree create/remove/list`). Useful but the v0.1.0 `superpowers:using-git-worktrees` skill is per-repo and works fine when a plan touches one repo at a time. → v0.3.
- **Per-repo test/lint/build runners** (`brm-repos test`, etc.). Sugar over `cd <path> && <cmd>`; roles can do this directly. → v0.3 if asked for.
- **Schema validation tools** (`brm-repos validate`). The `init` command writes valid files; manual edits are the user's responsibility for now. → v0.3.
- **`/conductor` role.** Considered and rejected for v0.2; existing roles cover orchestrator-mode work via the addendum. Re-evaluate if usage patterns show consistent friction. → v0.3 maybe.
- **Auto-detection of subrepos without `repos.yaml`.** Explicit configuration only. → No current plan.
- **Marketplace registration.** Same as v0.1.0 — deferred.
